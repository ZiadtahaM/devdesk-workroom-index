# DevDesk Public Content, Provenance, and Privacy Audit

## Scope

This audit covers the public landing-page source, document bootstrap, named workspace concepts, generated visual assets already hosted in project storage, and the two user-supplied reference collages. It does not treat browser logs, build output, repository metadata, dependency files, or internal app source as public marketing material.

## Public content disposition

| Content group | Decision | Rationale |
| --- | --- | --- |
| Core positioning: the people-aware operating layer | Preserve and elevate | It is the differentiated DevDesk promise and matches the existing product strategy. |
| Home, Inbox, Projects, and Team story | Preserve as reusable data | These are the clearest product proof surfaces and map to real operating questions. |
| GitHub connection simulation | Preserve with explicit simulation label | It demonstrates intended flow without falsely claiming a live integration. |
| Competitive focus view | Preserve with scoped language | It should explain product focus, not claim feature parity or superiority. |
| Repeated “not another project manager” phrasing | Consolidate | Keep the strongest version once in the positioning journey; use section copy to show proof instead of repeating the claim. |
| Dense seeded names and numeric workload examples | Keep as illustrative product-demo data only | They are useful to explain the interface but must remain visibly fictional and non-identifying. |
| Generic placeholder-style FAQ language | Tighten | Keep answers concise and explicitly distinguish beta capability from roadmap. |

## Provenance register

| Asset or claim | Provenance | Public-use decision |
| --- | --- | --- |
| Supplied university/editorial collage references | User-provided visual inspiration | Do not copy, crop into the site, or present as DevDesk work. Use only to inform compositional principles. |
| DevDesk hero image and brand mark | Earlier generated project assets in Manus storage | Retain with contextual alt text; use as branded visual support, not evidence of a live customer product. |
| Product screenshots, names, metrics, and repositories in the page | Simulated DevDesk demo content | Retain only with clear “preview”, “simulated”, or “illustrative” context. |
| Named competitor categories | Product-positioning synthesis | Describe broad focus categories; do not claim verified feature completeness, pricing, or market leadership. |
| Beta form data | User-entered future data | Do not expose, log, or render submissions publicly. A live backend must disclose retention and consent before release. |

## Privacy and accuracy boundaries

The public site must not display customer names, real repositories, private operational data, personal email addresses, or unsourced performance claims. The beta form is an interface-only prototype; it does not submit to a backend in the current static project. Any future form integration must include a clear data-use notice, minimal data collection, access controls, retention policy, and an explicit consent path.

## Reusable website information architecture

The premium rebuild will organize the public journey as **Signal → System → Proof → Integration → Choice → Beta**. This removes low-value repetition from the main surface while preserving valuable product evidence as reusable data-driven modules.

## Audit outcome

The public surface can retain the existing product promise, simulated interaction examples, generated brand visuals, and beta workflow. The supplied reference images remain private source inspiration and are excluded from public output. No customer testimony, claimed customer results, production integrations, or collected personal data will be represented as factual public content.
